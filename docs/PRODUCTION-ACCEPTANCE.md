# 生产验收与恢复演练

本手册用于单实例、持久本地磁盘的部署。执行测试使用专用实例和合成数据；浏览器业务验收按项目约定采用 Computer Use。下列流程是待执行的验收步骤，不代表已经在真实生产环境通过。

## 发布放行

1. 固定目标提交、版本和候选镜像 digest。Release 工作流先复用源码质量检查，再推送候选镜像，按 digest 完成镜像、旧库升级及生产 UI 验证，成功后才提升稳定标签。手动工作流只验证候选，不更新稳定标签。
2. 在与生产相同的 HTTPS 反代下完成下表；不得复用生产数据库或将 E2E 指向真实业务实例。
3. 完成空白实例恢复及容量检查，记录结果和证据位置。目标环境、基线数据量、负责人和告警接收人未填写时，不认定生产验收完成。
4. 保持原有 `latest` 镜像与 Watchtower 使用方式，无需新增变量或 profile。发布流水线只在验收成功后提升 `latest`；上线时记录实际镜像 digest，更新前创建可恢复备份。

| Computer Use 场景 | 验收标准 |
| --- | --- |
| HTTPS 登录、刷新、退出 | Secure Cookie 生效，退出后接口拒绝访问，错误信息不含凭据 |
| 管理员与两个普通账号 | 普通账号不能调用管理员接口，不能读取/修改其他账号私有对象 |
| 导航、项目、任务、日历 | 新增、编辑、删除、刷新后持久化正确；空态及失败提示明确 |
| 多标签与实时更新 | SSE 经过代理正常；陈旧工作区写入返回冲突且不覆盖新数据 |
| 移动屏幕与键盘 | 主导航、弹窗、焦点返回及关键操作可用，布局无整页横向溢出 |
| 可选 AI / Pro / 云存储 | 分别核对驱动与有效许可；测试成功、超时、无许可，禁止泄露密钥 |
| 管理员深度诊断 | 匿名/普通用户返回 403，管理员成功，再次频繁请求返回 429 |
| 恢复保护失败 | 在专用实例令备份目标不可写，恢复返回 503，原业务数据未变化 |

## 恢复材料清单

数据库快照不是整机恢复包。至少保管：

- 一致的 `navelix.db` 快照；文件级备份须停服，保留整个数据目录，不能运行中直接 tar 或只复制主库文件。
- 同一实例的 `data/.app_secret`，或部署时使用的原始 `APP_SECRET`。两者不可互换，不能用新生成的密钥替代原密钥。
- 数据目录中的头像等文件资源、`logs/settings.json`；如需要保留诊断历史，同时保留文件日志。
- 镜像版本及 digest、Compose / 反代配置和必要部署环境变量；许可与第三方服务凭据通过受控渠道保管。

密钥与备份存入访问受限、加密的异地介质。不要上传到 Git、工单或公共共享盘；不要把密钥写入命令行、截图和验收记录。使用 `APP_SECRET` 时通过原有 Secret 注入方式给恢复进程提供，避免在命令历史中留下值。

停服文件归档示例（先替换路径，确认备份目录不位于数据目录内）：

```bash
docker compose stop navelix
tar -czf /secure-backups/navelix-data-before-upgrade.tar.gz -C /opt/navelix data
chmod 600 /secure-backups/navelix-data-before-upgrade.tar.gz
docker compose start navelix
```

归档文件仍应进入加密存储；设置 0600 不是加密。归档失败须查明原因，不能将其记为成功备份。

## 空白实例恢复演练

1. 记录演练开始时间、目标 RPO（最多允许丢失多久数据）和 RTO（多久内恢复服务）。由维护者按实际需求填写目标，不能把默认每日备份等同于任何固定可用性承诺。
2. 使用独立卷/目录，恢复一致快照、文件资源及原始密钥，设置容器 UID/GID 的读写权限；在首次启动前完成密钥恢复，防止生成新实例密钥。
3. 在停服的恢复副本上验证库完整性与所有已知加密配置：

```bash
node scripts/recover-secrets.mjs --data-dir /absolute/restore-copy --confirm-offline
```

该命令默认只读数据库，不修改配置；缺少密钥时拒绝生成替代密钥。返回非零说明完整性或解密校验失败，停止后续放行。它检查 AI/天气密钥、Telegram Token 和云存储凭据，不输出明文。

4. 启动已记录的兼容镜像，检查轻量探针与管理员深度诊断；使用 Computer Use 验证登录、代表性记录和已加密外部服务配置，确认文件资源可读。
5. 在隔离实例增加新数据，再恢复快照，验证会话失效、审计历史保留和数据回退范围。记录实际丢失时间窗口与总恢复耗时，对照 RPO/RTO。
6. 升级回滚需恢复兼容镜像与升级前数据副本；只回退镜像不能保证 Schema 兼容。禁止修改迁移版本号伪造回滚。

## 历史固定密钥数据迁移

仅当确认历史版本因密钥文件异常使用过固定兜底密钥时适用。先停服并安全备份完整数据目录和原密钥；先在副本操作，再决定是否迁移真实实例。普通正常实例不需要该操作。

```bash
node scripts/recover-secrets.mjs --data-dir /absolute/offline-copy --confirm-offline --migrate-legacy-fallback
```

工具先生成权限为 0600 的保护性数据库快照，再验证每条密文：当前密钥可解密的保持原样，只有旧兜底密钥可解密的重新加密，其他密钥或损坏密文导致整个数据库写入事务回滚。没有原密钥时，该工具不能恢复由随机密钥加密的数据。迁移可能创建新 `.app_secret`，失败时保留它供重试；不要丢弃保护快照和密钥材料。

迁移后运行默认只读校验并完成恢复演练。旧保护快照含敏感配置，需安全保管；本工具不自动删除备份。

## 容量、故障与外部告警

在专用实例按预计数据量及两倍规模检查，记录并发用户/连接数、请求延迟分位数、错误率、CPU/内存、SQLite 锁等待及磁盘占用。阈值由维护者根据目标环境填写；未测量时不宣称支持任何固定并发规模。

- 同时保存导航、更新任务并保持 SSE 连接，确认没有丢失写入或长时间锁定。
- 在探针持续访问时验证业务延迟；公开 `/api/healthz` 仅执行常量规模读取，深度诊断每进程每分钟最多一次，仍应只按需调用。
- 在一次性数据卷模拟磁盘空间不足、不可写、重启和外部服务超时，确认错误可见且恢复/迁移不会丢失原数据。禁止在生产卷制造故障。
- 云备份启用后，检查管理员 `/api/admin/health` 返回的 `backup.lastCloudSuccessAt`（不要导出整个配置表）；重启后在过期时补跑，失败不推进成功时间，后续每小时重试。周期检查存在最长约一小时调度延迟，不能承诺严格 24 小时 RPO。
- 在宿主机或独立监控中探测 HTTP 状态与响应体 `status`，测试进程停止时确实告警；容器 unhealthy 本身不会保证自动重启。进程内 Telegram 无法覆盖应用完全停止。

## 证据记录

每次验收记录：提交、镜像 digest、平台与代理、数据规模、执行时间、检查项、预期/实际结果、脱敏截图或日志位置、未通过项、RPO/RTO 实测及负责人。共享记录不得包含账号密码、Token、数据库内容或密钥。
