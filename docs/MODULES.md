# 模块边界与流程组合

本规范适用于全系统的新增功能与重构。Navelix 使用模块化单体：在同一个 Next.js 应用内按业务职责组织，通过明确接口组合，不按组件行数或接口数量机械拆包。

## 依赖方向

- 页面负责组合；展示组件接收数据与回调，不直接请求 API、操作存储或驱动其他业务组件。
- Hook 管理界面状态、订阅、取消与请求生命周期。多个 Hook 可以在组合层协作，不另建用户状态真源；用户数据仍由 `NavelixProvider` 协调。
- 浏览器适配层位于 `lib/client/`，封装 HTTP、下载等浏览器能力，输入输出使用明确的 DTO。
- `lib/` 业务模块不引用页面、组件、Hook 或 Context。纯计算和数据契约不依赖数据库、浏览器、文件系统或业务单例。
- API 处理鉴权、请求解析和响应；业务入口继续负责归属校验、事务与外部请求安全。组合多个业务能力时，由上层显式注入接口；底层模块不反向导入调用方。
- 运行时导入不得形成循环；类型导入使用 `import type`。客户端的整个本地导入链不能引入 Node 内置模块或服务端能力。

## 业务职责与现有入口

| 模块 | 现有入口或边界 | 组合约定 |
| --- | --- | --- |
| 账号与安全 | `lib/auth.ts`、`lib/auth/`、`lib/profile.ts` | 会话与角色由守卫提供，写入入口保留鉴权及审计 |
| 用户配置与网址 | `context/navelix-context.ts`、`lib/user-data.ts`、`lib/share.ts` | 复用 Provider 与版本冲突检查，共享对象携带归属身份 |
| 项目与日程 | `lib/todos-projects.ts`、`lib/todo-store.ts`、相关 Hook | 明确传入账号、所有者与业务数据，事务由业务入口维护 |
| AI | `lib/ai-provider.ts`、`lib/ai-tools.ts`、AI API | 服务端持有密钥；工具调用复用业务入口及确认流程 |
| 通知与 Telegram | `lib/notification-store.ts`、`lib/user-notifications.ts`、Telegram 服务 | 发送前复核收件人、订阅与权限；通过公开能力投递 |
| 备份与恢复 | `lib/db-backup.ts`、`lib/db-restore.ts`、存储服务 | 备份、校验、还原的顺序由组合层负责，保留事务边界 |
| 日志 | `lib/logging/`、`lib/client/admin-logs.ts`、日志 Hook 与展示组件 | 采集、查询、清理、告警各自负责；业务不依赖日志界面 |
| 后台维护 | `lib/daemon/` | 维护模块分别暴露入口，由 daemon 编排调度 |
| CE/Pro | `lib/ee-bridge/`、`lib/ee-gate.ts` | 通过桥接契约组合，保持 EE 启动依赖限制 |

以上是职责索引，保留现有公开入口；不要求为了目录形式破坏兼容调用。

## 数据与事件序列化

跨 HTTP、持久化、导出和流程定义的契约使用 JSON 数据：字符串、有限数字、布尔值、null、数组与普通对象。时间使用时间戳或明确格式的字符串。禁止将函数、DOM、数据库连接、AbortSignal、Date、Map、循环对象和密钥塞入数据契约。

UI 回调、端口实现、鉴权上下文与取消信号属于运行时能力，通过参数注入，不进行序列化。跨进程或长期保存的格式应包含版本并在入口校验；功能内部临时对象不因这一要求强制转为 JSON。

## 步骤编排

`lib/workflows/types.ts` 定义版本化的 `WorkflowDefinition`；每步包含 `id`、`operation`、`input`。`definition.ts` 验证与复制计划，`execute.ts` 按序执行调用方提供的 operation 白名单，并向后续步骤提供前序输出。

- 整个计划及 operation 白名单在产生副作用前验证；不使用 eval、动态模块路径或数据中携带的代码。
- 取消立即停止后续步骤；步骤抛错后不再继续。取消信号在步骤间检查，能力实现可将 signal 继续传给请求。
- 数据最多 20 层、10,000 个节点、256 KiB；计划最多 100 步。输出同样接受 JSON 校验。
- 编排层不替代业务鉴权、危险操作确认或数据库事务；跨资源流程不能声称自动回滚，重试需要各能力自行保证幂等。
- 当前执行器用于进程内顺序组合，不提供持久队列、崩溃恢复、定时任务或自动重试。序列化的计划可以传输与检查，不代表运行中的能力或授权可以恢复。

日志管理已经接入：`management-workflow.ts` 提供“预览 → 确认 → 保存/清理”的计划与能力接口。Hook 注入 HTTP 和确认交互；用户取消或无需清理时终止后续执行。预览凭据只留在运行时能力中，不进入计划、输出或日志；服务端继续校验管理员、策略、有效期和一次性使用。

其他业务继续通过现有公开入口组合；新增跨功能流程按本规范实现，不能把尚未迁移的业务描述为已经接入执行器。

## 自动检查

`module-boundaries.test.ts` 使用 TypeScript AST 检查 `src/` 中的静态运行时 import、export 和字符串动态 import：全局无循环、客户端不依赖 Node、业务层不依赖界面层、工作流执行器不依赖具体业务。检查不执行应用模块，避免初始化真实存储；类型导入不算运行时依赖。

该检查覆盖本地源码的可解析依赖。外部包内部行为、计算得到的动态模块路径及运行时权限仍由构建、代码评审和流程测试验证。`workflows.test.ts` 覆盖序列化、执行顺序、取消、失败及日志组合。
